# دليل المطوّر

[English](../en-US/developer-guide.md) | [中文](../zh-CN/developer-guide.md)

هذا الدليل مُوجَّه للمساهمين الذين يوسّعون CyberStrikeAI. المشروع تطبيقُ خدمةٍ واحدة مكتوب بلغة Go، مع واجهة أمامية ثابتة (static)، وتخزين دائم عبر SQLite، وتنسيق Agent/MCP، وأنظمة فرعية أمنية اختيارية عالية الخطورة.

## بنية المشروع

```text
cmd/server/              نقطة دخول الخدمة
internal/app/            ربط التطبيق، المسارات، تسجيل أدوات MCP
internal/handler/        معالِجات HTTP
internal/database/       الوصول إلى SQLite
internal/security/       المصادقة، حدود المعدّل، تنفيذ الأوامر الصدفية (shell)
internal/mcp/            خادم MCP ومدير MCP الخارجي
internal/multiagent/     وكيل Eino المفرد، تعدّد الوكلاء، الوسيطات (middleware)
internal/workflow/       زمن تشغيل تنسيق الرسوم البيانية (graph orchestration)
internal/knowledge/      الفهرسة والاسترجاع
internal/c2/             الـ C2 المدمج
internal/project/        لوحة حقائق المشروع (blackboard)
web/static/              ملفات JS/CSS والأصول للواجهة الأمامية
web/templates/           قوالب HTML
tools/                   أدوات الأوامر بصيغة YAML
roles/                   أدوار بصيغة YAML
agents/                  تعريفات تعدّد الوكلاء بصيغة Markdown
skills/                  مهارات الوكيل (Agent Skills)
docs/                    التوثيق
```

## بدء التطوير

```bash
go run ./cmd/server --config config.yaml
```

الواجهة الأمامية ثابتة. معظم تغييرات JS/CSS/القوالب تتطلّب تحديث المتصفّح فقط.

## التحديث بنقرة واحدة: السماح لأي تثبيت بتحديث مصدره بنفسه

على جهازٍ منشور، يكون الروتين المعتاد هو: "تقدّمَت شجرتي بعشرات الـ commits ← ارفعْ هذا التثبيت ← أعدْ البناء ← بدّلِ الملف التنفيذي ← أعدِ التشغيل". كان هذا في السابق يقتصر على `upgrade.sh`، الذي كان يشير إلى مستودعٍ أصليّ (upstream) واحد ثابت؛ ولذلك كان "الترقية" بالنسبة لمن يشغّل نسخةً متفرّعة (fork) تعني "استبدال نفسك بكود شخص آخر". أمّا الآن فهذه الإمكانية تعيش داخل المنصّة (`internal/update`)، وتتشارك صفحةُ الطرفية (console) وواجهةُ REST وواجهةُ سطر الأوامر (CLI) تنفيذًا واحدًا، فلا يمكن للأسطح الثلاثة أن تختلف حول سبب رفض التحديث.

### نقاط الدخول الثلاث

| نقطة الدخول | كيفية الاستخدام |
|---|---|
| console | إعدادات النظام ← التحديث بنقرة واحدة (`#system-update`، والرابط العميق القديم ما زال يعمل). فتح هذا القسم يقرأ الشجرة المحلية فقط ولا يتّصل بالإنترنت؛ زرّ **Check** هو ما ينفّذ الجلب (fetch)؛ وزرّ **Update** يبدأ مهمّةً تستطلعها (poll) الصفحة؛ وخيار "الخروج بعد التحديث" يكون مُفعّلًا مسبقًا عند اكتشاف مُشرِفٍ (supervisor) (علامات إقلاع launchd/systemd)، وأثناء توقّف العملية تراقب الصفحة عودتها وتُعيد تحميل نفسها (الجلسات تعيش في الذاكرة، فيتبع ذلك تسجيلُ دخولٍ جديد)؛ ويوجد زرّ تراجُع (rollback) بالأسفل |
| REST | `GET /api/system/update` (الحالة من القرص، دون شبكة)، `POST /api/system/update/check` (جلب، ثم الإبلاغ عن الفارق)، `POST /api/system/update/apply` (يُرجِع `202` مع `job_id`، يُستطلَع عبر `GET /api/system/update/job`)، `POST /api/system/update/rollback` |
| CLI | `./cyberstrike-ai -check-update`، `./cyberstrike-ai -update`، `./cyberstrike-ai -update-rollback`. جذرُ التثبيت هو المجلد الذي يحتوي `--config`، أو المجلد الحالي حين لا يُمرَّر `--config` |

الصلاحيات هي `update:read` (للطلبات GET) و`update:apply` (لنقاط النهاية الأربع المُعدِّلة). كما يتطلّب `update:apply` إضافيًّا جلسةً عامّة (نطاق `all`): فلكلّ جهازٍ شجرةُ مصدرٍ واحدة، ويجب ألّا تتمكّن جلسةٌ من نوع `assigned`/`own` من تحريك الكود الذي يشغّله الجميع.

### من أين يأتي الكود

من **مستودع مصدر التحديث**: عنوانٌ واحد، وهو المستودع الرسمي `https://github.com/AIPentest/CyberStrikeAI.git` افتراضيًّا، ويتبع التحديثُ **الفرعَ الافتراضيّ الخاصّ بذلك المستودع** (لا شيء يُضبَط بخصوص الفروع، و"main" ليس مُرمَّزًا بشكل ثابت)؛ ولذلك فإنّ تثبيتًا بلا أيّ إعداد على الإطلاق ما زال لديه إجابةٌ واحدة بالضبط عن سؤال "من أين يأتي التحديث". وصار `upgrade.sh` غلافًا رقيقًا فوق التنفيذ نفسه: فحين يكون هذا المجلد شجرةَ عملٍ git، يكتفي باستدعاء `./cyberstrike-ai -update`.

### تغيير المصدر (قسم update في config.yaml)

مصدرُ التحديث حقلٌ واحد: عنوان مستودع. القيمة الفارغة تعني المستودع الرسمي؛ ولتتبُّع نسختك المتفرّعة، أو مرآةٍ (mirror) (حين يصعب الوصول إلى GitHub)، أو مستودع شخصٍ آخر، فهذا هو المكان الوحيد الذي تُغيّره:

```yaml
update:
  repo: https://github.com/AIPentest/CyberStrikeAI.git  # عنوان مستودع واحد؛ فارغ/غائب = المستودع الرسمي
```

كتلة "Update source" في الـ console تُحرِّر هذا العنوان وتحفظه (حفظُه فارغًا يُعيدك إلى المستودع الرسمي). ويتحقّق الحفظ من العنوان مقابل قائمة سماح (allowlist): https/http/ssh/git/file إضافةً إلى المسارات المحلية المطلقة — أمّا نقل git عبر `ext::` فيُنفّذ أوامر، ولذلك يُرفَض رفضًا قاطعًا.

### ربط تثبيتٍ ليس من نوع git (نوع الأرشيف المضغوط tarball)

التثبيت الذي بدأ كأرشيف Release مفكوك الضغط لا يملك `.git`؛ ويمكن ربطه من الصفحة نفسها (المستودع الرسمي الافتراضي يعمل دون أيّ إعداد): تُجري المعاينةُ الجلبَ في مستودعٍ مؤقّت، وتسرد أولًا **الملفات المحلية التي سيستبدلها الهدف** و**محتوى المُشغِّل (operator) الذي سيُحتفَظ به**؛ وعند التأكيد يصير المجلد شجرةَ عملٍ git (‏`git init`، إضافة origin، سحبُ الفرع الهدف)، ويُحتفَظ بكلّ ملفٍّ مُستبدَل تحت `.update-backup/<unique-backup>/overwritten/`، ويُخبَّأ محتوى المُشغِّل (stash) ويُستعاد كالمعتاد، ويُعاد بناءُ الملف التنفيذي. ومن تلك اللحظة يصبح تثبيتًا عاديًّا بتحديثٍ بنقرة واحدة وتراجُع — لكن انتبه إلى أنّه لا يوجد تاريخُ git قبل الربط، فالربطُ نفسه ليس له commit سابق يُتراجَع إليه؛ وأوّلُ تحديثٍ حقيقيّ يكتب أوّلَ نقطة تراجُع.

### رقم الإصدار يتبع الكود

يحمل ملف `config.example.yaml` في المستودع رقمَ الإصدار الذي قُطِع منه هذا الكود (يزيده المستودعُ الأصليّ في commit الإصدار)، بينما ملفُّك `config.yaml` بياناتُ مُشغِّلٍ لا يمسّها أيّ تحديث. ولذلك فبعد دمجٍ ناجح يكتب التحديثُ رقمَ إصدار الكود الجديد في حقل `version` داخل `config.yaml` (ذلك السطر وحده، عبر ملفٍّ مؤقّت ثم إعادة تسمية ذرّية؛ ويسجّل سجلُّ المهمّة الرقمَ القديم والجديد). وبعد إعادة التشغيل يتطابق كلٌّ من شارة الترويسة والمَعلَمة `?v=` للأصول الثابتة مع الكود مجدّدًا — وهذا أيضًا سببُ إبطال الواجهة الأمامية لذاكرتها المؤقّتة من تلقاء نفسها عند الترقية. والتراجُع يُعيد الرقم كذلك (ما لم يكن أحدٌ قد عدّله يدويًّا في هذه الأثناء)، وربطُ تثبيتٍ من نوع tarball يزامنه أيضًا.

### أسباب الرفض الأربعة

| الحالة | السبب | المعنى وما ينبغي فعله |
|---|---|---|
| تعديلٌ محلّيّ على **مصدر** المنتج (مسارٌ خارج القائمة المحميّة) | `local_source_edits` | التحديث تنزيلٌ لا قرارُ دمج. أسماء الملفات مسرودة؛ نفّذْ لها commit أو استعدْها أولًا |
| **تباعُد** الفرع عن بعيده (متقدِّمٌ ومتأخِّرٌ في آنٍ واحد) | `diverged` | ذلك قرارُ دمج؛ تُبلَّغ الأعداد لتحلّه يدويًّا |
| لا توجد سلسلة أدوات Go على هذا الجهاز | `no_toolchain` | **المصدر يُحدَّث رغم ذلك**؛ لا يُبدَّل سوى الملف التنفيذي. ثبِّتْ `go` واضغط التحديث مرّةً أخرى للإتمام |
| هذا المجلد ليس شجرةَ عملٍ git | `not_a_repo` (‏`installed: false` في الحالة) | تثبيتُ tarball لا يملك بعيدًا لِيُسرَّع إليه (fast-forward)؛ حدِّثه عبر حزمة الإصدار |

عملية `apply` غير متزامنة، فتُجيب دائمًا بـ `202` أولًا، وتصل أسبابُ الرفض أعلاه في حقل `job.failure` المُستطلَع (‏`reason` / `message` / `items`). أمّا `rollback` فمتزامنة وتُطابِق أسبابَ الرفض برموز الحالة (‏`local_source_edits`، `diverged`، `no_state`، `moved_since_update`، `no_binary` ← 409، وأيُّ شيءٍ آخر ← 400). والإخفاقات الأخرى (‏`merge_failed`، `build_failed`، `swap_failed`) تحمل مُخرَجات git أو المُصرِّف (compiler) نفسها؛ والبناءُ الفاشل يُبقي الملفَّ التنفيذيَّ السابقَ في مكانه بينما يكون المصدرُ قد تحرّك بالفعل وكُتِب ملفُّ الحالة، فيبقى قابلًا للتراجُع.

تتشارك عملياتُ الفحص والتحديث والتبنّي (adoption) والتراجُع وإعادة التشغيل قفلَ ملفٍّ على مستوى نظام التشغيل في مجلد التثبيت (`.update-lock`). انتظرِ العمليةَ الأخرى حين يُبلَّغ `update_busy`. ويحرّر النظامُ القفلَ عند خروج عمليّته؛ لا تحذفْ ملفَّ القفل للالتفاف عليه.

### كيف يبقى محتوى المُشغِّل

المسارات `roles/ skills/ tools/ agents/ knowledge_base/ data/ log/ venv/ config.yaml .env` تخصّ **المُشغِّل** (والحَكَمُ هو `update.Protected`). قبل الدمج، تُنسَخ فقط تلك المسارات التي يكتب إليها التحديثُ فعلًا إلى `.update-backup/<unique-backup>/` وتُزال من الشجرة — أمّا مجلداتك الإضافية التي لم يمسّها المستودعُ الأصليُّ قطّ فلا تُمسّ — ثم تُعاد بعد ذلك، وهذا هو معنى "حدِّثِ الكود، واحتفظ بعملي". وتُسمّي النتيجةُ كلَّ ملفٍّ في `keptContent` بدلًا من إسقاطه بصمت: فحيثما غيّرتَ أنت والمستودعُ الأصليُّ الملفَّ نفسه، تكون النسخةُ التي تَثبُت هي نسختَك، وتقول النتيجةُ ذلك.

### التراجُع (Rollback)

‏`./cyberstrike-ai -update-rollback`، أو الزرّ في الصفحة: ‏`git reset --hard` رجوعًا إلى الـ commit الذي جاء منه التحديث، ويُعاد الملفُّ التنفيذيُّ المحفوظ باسم `cyberstrike-ai.prev` حين كان ذلك التحديثُ قد بدّل واحدًا، ويُزال `.update-state.json`. والتحديثُ الذي فشل بناؤه لم يبدّل ملفًّا تنفيذيًّا قطّ، فتراجُعه يحرّك المصدرَ فقط — إذ إنّ الملفَّ التنفيذيَّ الموجود على القرص يخصّ بالفعل الـ commit الذي يعود إليه. ويرفض التراجُعُ حين لا يوجد سجلُّ تحديث (`no_state`)، أو حين يكون التبديلُ مستحقًّا ولا يتبقّى `cyberstrike-ai.prev` (`no_binary`)، أو حين لا يكون الـ commit المُسجَّل موجودًا في هذا المستودع (`bad_state`)، أو حين لا يكون الملفُّ التنفيذيُّ على القرص هو الذي يقرنه السجلُّ بذلك الـ commit (`binary_changed`)، أو حين **تحرّك HEAD منذ ذلك التحديث** (`moved_since_update` — فالتراجُع يُلغي التحديثَ لا العملَ المُنجَز بعده)، أو حين يكون المصدرُ مُعدَّلًا محلّيًّا (`local_source_edits`).

يكتب التراجُعُ ملفَّ `.update-rollback-pending.json` قبل تغيير المصدر أو الملفات التنفيذية. شغِّلِ التراجُعَ مرّةً أخرى بعد انقطاعٍ لإتمام الاستعادة؛ وتُبلِّغ الـ console عن `rollbackPending` وتوقِف التحديثاتِ الجديدة مؤقّتًا. احتفظْ بسجلّ الاستعادة ومجلد النسخ الاحتياطي وملفّ `.prev`. وإذا لم تتطابق تجزئاتُ (hashes) الملف التنفيذيّ المُسجَّلة مع الملفات على القرص، فإنّ الاستعادة ترفض الكتابةَ فوقها.

### حالتا إعادة التشغيل

لا تنسحب العمليةُ (إغلاقٌ متدرّج `Shutdown` ثم خروجٌ بالرمز 0) إلّا حين يقول الطلبُ صراحةً `restart: true` **و** يكون خطّافُ (hook) إعادة التشغيل قد وُصِّل عند بدء التشغيل. أمّا عودتُها فعلًا فمتروكةٌ لمُشرِفٍ (systemd، `run.sh`)، وتقول الصفحةُ ذلك بالضبط بدلًا من الوعد بإقلاعٍ قد لا يحدث. وطلبُ إعادة التشغيل دون خطّافٍ موصَّل يُرجِع `400`، بدلًا من إيقاف الخدمة وادّعاء أنّها أُعيد تشغيلها.

**الملفُّ التنفيذيُّ المُعلَّق حالةٌ دائمة، ويمكن تفعيله لاحقًا.** تقارن نقطةُ نهاية الحالة هُويّةَ الملف التنفيذيّ المُلتقَطة عند بدء التشغيل (الحجم + mtime بدقّة النانوثانية) بما هو على القرص الآن: فبعد تحديثٍ أو تراجُعٍ أو تشغيلِ CLI بدّل الملفَّ دون إعادة تشغيل، يصير `needsRestart` صحيحًا (true)، ويقول `binaryBuiltAt` متى بُنِي، وتُنمي الـ console لافتةً دائمة فيها **Restart now** (‏`POST /api/system/update/restart`؛ ‏`409 nothing_pending` حين لا يوجد ما يُفعَّل، و`409` أثناء تشغيل مهمّة، و`400` دون خطّاف). ويأتي حقل `supervised` من علامات بيئية (‏`XPC_SERVICE_NAME` في launchd، و`INVOCATION_ID`/`JOURNAL_STREAM` في systemd) ولا يقرّر سوى القيمة الافتراضية للخيار.

**والصفحة تتعافى من تلقاء نفسها.** أثناء توقّف العملية تصير الـ console عرضَ استعادةٍ يسبُر نقطةَ نهاية الحالة كلّ ثانيتين: فالرمز 200 يعني أنّ العملية القديمة ما زالت تُجيب (واصلِ الانتظار)، والاتّصالُ الميت يعني أنّها في طريقها إلى الخروج، والرمز 401 من عمليةٍ لم تعُد تعرف الجلسة هو الدليلُ على أنّ إعادة التشغيل حدثت — عندئذٍ تُعيد الصفحةُ توجيه نفسها عبر `location.replace` رجوعًا إلى `#system-update`. ومغادرةُ الـ console توقِف المراقبةَ بدلًا من انتزاع المستخدِم رجوعًا.

## إضافة وحدة أعمال (Business Module)

لا تضفْ معالِجًا فقط. الوحدةُ الكاملة تحتاج عادةً إلى:

1. نموذج بيانات وهجرة (migration) لـ SQLite.
2. معالِج: المعاملات (parameters)، الأخطاء، التقسيم إلى صفحات/الترشيح.
3. تدقيق (Audit): إجراءات الإدارة.
4. مراقبة (Monitor): حالة التنفيذ طويل الأمد.
5. MCP: هل ينبغي للوكلاء استدعاؤها.
6. HITL: حدّ الموافقة البشرية لأدوات MCP.
7. OpenAPI: حدِّثْ `/api/openapi/spec`.
8. الواجهة الأمامية: التدويل (i18n)، الحالات، واجهة الفراغ/الخطأ.
9. الاختبارات: قاعدة البيانات، المعالِج، الحالات الحدّية.
10. التوثيق: الإعداد، الاستخدام، حلّ المشكلات، الأثر الأمني.

إغفالُ أحد هذه عادةً ما يتحوّل لاحقًا إلى خللٍ في قابلية الاستخدام أو في الأمان.

## تصميم استجابة الخطأ

فضِّلِ استخدام JSON ثابتًا:

```json
{
  "error": "machine_readable_code",
  "message": "human-readable explanation"
}
```

الواجهةُ الأمامية تحتاج حقولًا ثابتة، والمستخدِمون يحتاجون رسائل قابلة للتنفيذ، والسجلّات تحتاج أخطاءً داخلية مفصّلة.

## المهامّ طويلة الأمد

للفحص (scanning)، والفهرسة، والمهامّ الدُّفعية (batch)، والـ C2، أو العمليات الخارجية، أجِبْ عن:

- هل يمكن إلغاؤها؟
- هل يمكن الاستعلام عن التقدّم؟
- هل يمكن إعادة محاولتها؟
- أين يُخزَّن الناتج؟
- هل تبقى الحالةُ بعد تحديث الصفحة؟
- هل تحجب طلبَ HTTP؟

إنْ لم يكن كذلك، فاستخدمْ جداولَ المهامّ، أو تدفّقاتِ الأحداث (event streams)، أو المراقبة.

## توسيع الأدوات

فضِّلْ `tools/*.yaml` لأدوات الأوامر. استخدمْ أدوات Go المدمجة حين تحتاج الأداةُ إلى حالةٍ داخلية أو تكاملٍ مُهيكَل.

ينبغي للأدوات المدمجة أن تُعرِّف مخطّطاتِ إدخالٍ واضحة، وأن تعالج المهلاتِ والأخطاء، وأن تحترم HITL للإجراءات الخطِرة.

## تغييرات الواجهة الأمامية

استخدمِ المساعِدات الموجودة مثل `apiFetch`، وأدوات النوافذ المنبثقة (modal)، والإشعارات، والتدويل (i18n). حدِّثْ كلًّا من `web/static/i18n/zh-CN.json` و`web/static/i18n/en-US.json` لأيّ نصٍّ مرئيٍّ جديد.

تجنّبْ وضعَ الأسرار أو مفاتيح المزوّدين في كود الواجهة الأمامية.

## أولوية الاختبار

اختباراتٌ عالية القيمة:

- التطبيق الحيّ للإعدادات (config hot-apply)؛
- فروع HITL؛
- مهلة الصدفة/انعدام المُخرَجات (shell timeout/no-output)؛
- استعادة MCP الخارجي؛
- فهرسة قاعدة المعرفة (KB) والمعالجة اللاحقة؛
- كشف نظام التشغيل/الترميز في WebShell؛
- توافق هجرة SQLite.

## مراسي المصدر (Source Anchors)

- ربط التطبيق: `internal/app/app.go`
- تطبيق الإعدادات: `internal/handler/config.go`
- OpenAPI: `internal/handler/openapi.go`
- مُنفِّذ الأدوات: `internal/security/executor.go`
- حزمة المهارات: `internal/skillpackage/`
- التحديث بنقرة واحدة: `internal/update/` (الحالة، التطبيق، التراجُع)، وسطحُ HTTP في `internal/handler/update.go`، ومفاتيحُ CLI في `cmd/server/update_cli.go`، والغلافُ الرقيق في `upgrade.sh`

### أدلّة الاستعادة وتعديلات تفعيل MCP

تتحقّق استعادةُ التحديث الذاتيّ من أسماء حقول JSON وأنواعها، والمفاتيح المكرّرة، وعلاقات الـ commit/التجزئة، وملفات الملف التنفيذيّ الفعلية، قبل استئناف تغييرات نظام الملفات. ولا تزال علامةُ البناء القديمة النصّية مدعومة، لكنْ يُتحقَّق أيضًا من أيّ حالةٍ (State) مُرافِقة. والسجلُّ الغامض أو الناقص أو غير المدعوم يُرفَض مع الحفاظ على الملفات وأدلّة الاستعادة. لا تحذفْ سجلًّا مُعلَّقًا لمجرّد الالتفاف على الرفض: صالِحْ أولًا بين commit المصدر، والملف التنفيذيّ الحيّ، والملف التنفيذيّ السابق/النسخة الاحتياطية.

تحريرُ MCP خارجيٍّ قائم دون حقول تفعيل يحفظ حالتَه الحالية مُفعَّلًا/موقوفًا (enabled/stopped). أمّا الحقول الصريحة `disabled` أو `external_mcp_enable` فتغيّر التفعيل؛ و`disabled: true` له الأولوية. والخادم الجديد يكون افتراضيًّا مُفعَّلًا. كما يُديم كلٌّ من البدء/الإيقاف حالةَ `disabled` المقابلة، فلا يؤدّي تحريرُ التطبيق أو إعادةُ تشغيله إلى تفعيل خادمٍ موقوفٍ بصمت.
